## 1. 지시 · 완료 정의 · 범위

- **지시 요약**: 「명확히 문서화해서 그 문서로 검증까지 하는게 목적」(사용자, 2026-10-15). 시범 대상 원주시의회는 사전 분석이 있어 Claude가 제안했다(R01-결1, 사람 확정 아님).
- **완료 정의**:
  1. 수집이력 로그에서 건수가 어떻게 보이는지 가장 먼저 확인한다(SSOT 9장 6번 답).
  2. D1~D4 판정이 나온다(D5는 권장). D4는 건수 대조와 필드 대조(로그 확인·첨부 포함)를 모두 마친 결과다(SSOT 6장 8단계).
  3. SSOT 9장 1번의 `##`·`\"`(D3 수집테스트와 D4 1회차 건수로 실측, R01-결7 — `#`·`.`·name 표기는 2차 설명 회의로 부분 답)과 ~~5번(답 대기)~~ → 5번(2026-10-15 화면 확인으로 답. thid 조회 칸은 있으나 창에 상세가 실제로 뜨는지는 view_url을 고친 뒤 D2에서 확인 — 미확인, §G9)의 결과가 7절에 기록된다. 나머지 질문은 2026-10-15 답과 2차 설명 회의를 SSOT에 반영했다.
  4. '사전 분석 예상 vs 실측' 표의 G1~G6이 실측으로 판정된다.
  5. 단계별 소요 시간이 기록된다. 필드 대조는 건당 소요 시간도 적는다(9장 13번 판단 자료).
  6. 수집이력에서 1회차 완료로 볼 표시(상태 값·종료 시각 등)와 실제 걸린 시간, 로그의 어느 줄에 건수가 뜨는지, '정규식 패턴 JSON 입력'의 위치와 형식을 실측해 적는다(SSOT 4장, 6장 6·8단계에 통합 때 반영). 같은 대수를 다시 수집하는 일이 생기면 그 회차에 새로 수집되는지도 확인한다(9장 12번 해석, R01-결5).
  7. 10대가 '다음' 버튼 없이 첫 페이지에서 멈추면 R01-결8대로 처리하고, 커스텀이 되면 7절 '커스텀 후보'에 적는다(§G1, SSOT 13장).
  - **중간 게이트**: D4 ~~건수 대조가~~ → 건수·필드 대조가(2026-10-15, 2차 설명 회의로 D4에 필드 대조가 추가된 데 따른 정정 — 게이트 포함은 사람 확정 아님. 끝의 뜻은 SSOT 6장 10단계, 범위는 9장 13번) 끝나면 템플릿 v1을 동결하고 본 검증을 시작한다(SSOT 0장 11번). R01의 나머지는 본 검증과 겹쳐 진행한다.

## 사전 분석 (2026-10-15, D1 일부)

2026-10-15에 실제 사이트와 대조한 결과, 기존 설정은 9대 기준이고 10대는 '다음' 버튼이 없어 페이징 방식에 따라 누락될 수 있다. 기대 건수는 10대 77건(8페이지), 9대 1,161건(117페이지)이다. 수집설정관리에서 원주시의회는 지방의회_의안과 5분 자유발언에 O가 있다.

| 파라미터 | 기존 설정값 | 확인 결과 |
| --- | --- | --- |
| paging_selector | `#pagingNew` | 1개 매칭 |
| next_btn_selector | `.next` | 9대는 `a.btn.next` 있음, 10대는 모든 페이지에 없음 |
| list_class | `div.board_list` | 페이지당 10행, 모든 행에서 thid 추출 |
| view_class | `ul.bill-list` | 상세에 2개: 기본정보 9항목, 위원회·본회의 처리사항 3항목. 둘을 감싸는 영역은 `div.bill-view` |

- 대수 option의 value는 `?s_daesu=9&…` 형태이고, 선택하면 바로 페이지가 바뀐다(SSOT 9장 4번).
- '다음' 버튼 대체 후보 `#pagingNew li:has(> a.select) + li > a`는 10대 1→2·2→3페이지 이동과 8페이지 종료, 9대 10→11페이지 이동과 117페이지 종료를 확인했다. 수집기가 `:has()`를 지원하고 이 셀렉터로 페이지를 넘길 때만 쓸 수 있다(SSOT 9장 2번).
- 2차 설명 회의(2026-10-15)에서 수집기가 '다음' 버튼으로 페이지를 넘기고 버튼이 없을 때의 예외 처리가 없다고 확인됐다(SSOT 9장 2번 답). 그래서 10대는 첫 페이지 10건에서 멈출 가능성이 높다(예상 1번, R01-결8).
- 상세는 `billList.html?pg=vv&thid=…` URL만으로 열려(위 view_id_param), 상세 접근 불가로 커스텀이 될 가능성은 낮다(SSOT 3장 view_url, 사전 분석, 미실측).
- 기존 설정값은 사용자가 보낸 수집 설정 화면 캡처 기준이다(전사(작성: 최민규), ~~GUI 실측 전~~ → 2026-10-15 GUI 상세 화면(수집 ID 28, 보드타입 bill)에서 파라미터 값을 읽어 위 표와 같음을 확인했다 — 화면 확인, 버튼은 누르지 않음). search_form_selector 값에는 백슬래시가 실제로 들어 있다(§G5).
- 같은 날 화면 확인(SSOT 14장):
  - 목록의 의안 'O'는 수집 ID 28·보드타입 bill(BBS '의안')을 연다. 수집이력의 원주 의안 행은 매시 30분 무렵 두 번씩 생기는 정기 수집이다(388건). 본 최근 10행은 데이터 건수가 모두 0이다. 그중 상세를 연 388번 행(LOG ID 25915)은 수집 ID 10028·보드타입 billTemp('의안_검증')였다. 같은 시각의 다른 한 행이 어느 설정인지는 열어 보지 않았다(미확인, §G7). ~~어느 설정이 검증 대상인지는 SSOT 9장 15번(R01-결11).~~ → 검증 대상은 bill(수집 ID 28)이다(SSOT 9장 15번 답, 2026-10-15).
  - 정규식 도구 창 확인(2026-10-15, 사용자 요청): '의안_종류_이름' 규칙 행 [선택] → 창이 처음 "선택 가능한 상세 영역을 찾지 못했습니다"를 띄웠다. 상세 고유값 4490으로 조회하자 `billList.html?thid=4490`을 불러왔는데, 이 주소는 사이트에서 목록(검색) 화면이다. 상세는 `pg=vv`가 있어야 열린다. 그래서 D1에서 view_url부터 확인한다(§G9, SSOT 14.7). 창은 [취소]로 닫았고 아무것도 적용·저장하지 않았다.
  - 같은 확인에서 본 규칙 표: 부모 컬럼 47개, 규칙 행 17개. 본회의·위원회 처리사항 컬럼(본회의_처리_일자·위원회_결과 등)에도 정규식이 걸려 있어, 처리사항은 수집 대상 컬럼이다(§G2 — 필드 대조에서 빠지면 빠진 필드로 본다).
  - 수집이력 상세의 수집 기관 사용여부는 '미사용'으로, 목록의 수집 여부 '사용'과 다르다. 뜻은 확인하지 않았다(미확인).
  - 상세의 ☐ 기존데이터 삭제는 해제 상태였다(SSOT 14.3).

## 3. 건수·필드 대조 (D4) — 기준 건수 먼저 고정

- 추가 수집 **전에** 사이트 건수·근거·기준 고정 시각(YYYY-MM-DD HH:MM)을 다시 확인해 적는다. 아래 값은 2026-10-15 사전 확인값이다. 값이 같으면 기준 고정 시각만 재확인 시각으로 바꾸고, 다르면 값을 바꾸고 사유 칸에 「재확인: 이전 값 n건(시각)」을 적는다.
- 대수별로 따로 적고 **합산하지 않는다**. 9대(직전)를 먼저, 10대(최근)를 나중에 수집한다(SSOT 6장 6단계).
- 수집 건수는 그 회차의 수집 건수다(다시 수집하면 새로 수집 — 9장 12번 답의 해석, R01-결5). 같은 대수를 다시 수집했으면(R01-결8·결10) 회차를 늘려 새 줄로 적고, 실측으로 확인되기 전까지 재수집 회차의 판정에는 '(잠정: 9장 12번)'을 붙인다. 다르게 보이면 사유 칸에 적는다.
- 차이가 수집 시각 이후에 등록된 글 때문이면 그 근거(등록일)를 적는다. 차이가 0이면 사유 칸은 '해당 없음'.
- 실측 근거의 목록 URL은 착수 때 전체 URL로 바꿔 적는다.
